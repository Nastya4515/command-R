## 1. Что требует кейс

Источники: `ВИНИТИ+ЮФУ.pdf` (условия), README участников обоих архивов, README шаблонов сдачи.

**Задача.** Из PDF научных статей извлечь объекты, показатели, условия и результаты. Для каждого значения сохранить
источник (страница PDF, раздел, таблица/рисунок, дословная цитата) и статус записи. Неизвестное **не достраивается по догадке**.
Нарушения правил сохраняются как замечания; исходная запись не удаляется.

**Две предметные области** (можно одну или обе). Общие этапы извлечения и проверки должны работать
**независимо от состава предметных полей** — это прямое требование условий (стр. 2).

| | Область 1 — тонкоплёночные солнечные элементы | Область 2 — RAG |
|---|---|---|
| Таблицы сдачи | publications, materials, devices, layers, measurements, results, issues | publications, configurations, datasets, tasks, experiments, results, issues |
| dev / test | 21 / 90 PDF + эталон dev (659 результатов, 519 слоёв, 89 приборов) | 21 / 90 PDF (3 и 14 — синтетические сканы без текста) + эталон dev (37 616 результатов, 4 733 конфигурации) |
| Закрытые словари | material_class, device_role, architecture, layer_function, scan_direction, aggregation, metric_name… | in_scope, result_origin, extraction_status |
| Нормализация | PCE/FF — %, Voc — V, Jsc — mA/cm², Eg — eV, толщина — nm, площадь — cm², время — h | только при известной шкале; исходное значение сохраняется |
| Правила проверки | PCE = Voc·Jsc·FF/Pin (±3 % отн.), Voc < Eg/q, пределы Jsc/FF/PCE, Jsc(EQE) vs Jsc(ВАХ) > 5 %, champion vs mean, прямой/обратный ход отдельно | шкала метрики, k для @k, связь результата с конфигурацией/набором/задачей/протоколом, разные эксперименты не объединяются |
| Сопоставление | класс материала, тип прибора, AM1.5G 100 мВт/см², площадь, агрегация, направление развёртки | задача, набор данных, определение метрики, протокол |
| Проверка формата | `tools/check_submission.py` (свой у каждой области) | `tools/check_submission.py` (+ `--ocr`) |

**Что сдаётся (стр. 11):** 1) набор данных (CSV по test) · 2) паспорт набора (поля, типы, размерности, правила) ·
3) интерфейс (поиск, фильтры, источник, проверки) · 4) результаты проверки (противоречия и причины замечаний).
Оценка — по эталону test (у организаторов) и независимым проверочным примерам, единая шкала для обеих областей.

Архив RAG по содержанию совпадает с уже лежащим в `data/` (отличия — переводы строк и опечатка в README шаблона).
Архив области 1 в проекте отсутствует.

## 2. Оценка текущего проекта (ветка `dev`, коммит f6a1448)

### Что хорошо и сохраняем
- Конвейер по шагам `read_pdf → fragments → model → assemble → export → check` с кэшем каждого шага: повторный запуск продолжает с места сбоя, ответы модели не оплачиваются дважды.
- Чтение PDF двумя движками (PyMuPDF + pypdf), склейка строк таблиц, детектор сканов и vision-OCR через модель.
- Клиенты модели за единым интерфейсом: `api` / `mock` / `file` / `local`, ретраи, логирование токенов.
- Интеграция официального `check_submission.py` в конвейер.
- Бэкенд FastAPI + DuckDB: поиск, фильтры, сортировка, пагинация, экспорт CSV, карточка записи со связями, загрузка PDF с фоновой обработкой и опросом статуса.
- Фронтенд: Обзор (3D-сфера), Загрузка (drag-and-drop + лог), Данные, Замечания, Публикации, боковая карточка записи.
- Тесты pytest + ruff.

### Критичные проблемы
1. **Модель видит только кусочки.** Ей дают строку таблицы или окно ±12 слов вокруг числа и просят «метрика | значение». Поэтому:
   - `configurations` — только подпись строки таблицы как `rag_variant`, остальные 18 полей пусты;
   - `datasets`, `tasks` — **всегда пусты**; `experiments` — одна заглушка `E1` «mock pipeline»;
   - у результатов `dataset_id`, `task_id`, `metric_variant`, `metric_direction`, `aggregation` фактически не заполняются.
   Это 4 из 7 таблиц и половина полей results — основная часть оценки.
2. **Метаданные публикаций эвристические:** title — по размеру шрифта, `authors` всегда пусто, `in_scope` всегда `true` (исключённые статьи не распознаются).
3. **Цифра качества 81 % не настоящая.** Она получена на `MockClient`, который «отвечает» прямо из эталона dev. Это потолок конвейера, реальная точность модели не измерялась. `score.py` сравнивает только тройку (статья, метрика, число) и не проверяет связи, источник и дубли.
4. **Область 1 не поддерживается вообще** — ни конвейер, ни бэкенд, ни интерфейс (колонки RAG зашиты в код).
5. **Подсветка источника потеряна.** В коммитах 64eb0f1 / f108af3 / bec2c63 цитата подсвечивалась жёлтым `<mark>` (но в макете с выдуманным текстом). В f6a1448 источник стал настоящим PDF в `<iframe>` — без подсветки.

### Мелкие проблемы
- Нет экрана «Сравнение» (прямо названо в условиях — «сопоставление»), нет паспорта набора.
- Кнопка «Настройки» ничего не делает; на «Обзоре» нет переключателя набора (dev/test/uploads).
- В git лежит `reports/check_dev.json` на 49 тыс. строк.
- Исправлено сегодня: падение бэкенда на пустой базе и при параллельных запросах (DuckDB 2.0), запуск `npm run server` на Windows.

## 3. Целевая архитектура

### 3.1. Ядро, не зависящее от области — «профиль области»
Каждая область описывается декларативным профилем `domains/<area>/profile.yaml` (+ JSON-схема ответов модели):
таблицы и поля, ключи и связи, закрытые словари, целевые единицы, промпты, предметные правила проверки, правила сопоставления.
Общий код (чтение PDF, вызов модели, проверка цитат, нормализация чисел, дубли, экспорт, проверка, интерфейс) берёт всё из профиля.
Новая область = новый профиль + модуль правил, без правки ядра.

### 3.2. Конвейер извлечения v2
```
PDF ─► read_pdf ─► pages (текст по страницам; скан → vision-OCR)
        │
        ├─► A. Документ целиком (1–2 вызова LLM, structured outputs / JSON-схема):
        │      библиография, in_scope + причина исключения,
        │      сущности области: RAG — конфигурации, наборы, задачи, эксперименты;
        │                        Solar — материалы, приборы, слои, условия измерения.
        │
        ├─► B. Постранично (вызов на страницу/таблицу, с перечнем сущностей из шага A):
        │      результаты: метрика, значение, единица, агрегация, k,
        │      связи с сущностями, primary/cited, раздел/таблица/рисунок,
        │      ДОСЛОВНАЯ цитата.
        │
        ├─► C. Верификация (код, без LLM):
        │      цитата найдена на указанной странице (та же нормализация, что у check_submission),
        │      число из цитаты совпадает со значением, ссылки на сущности существуют,
        │      значения словарей допустимы. Не прошло → повторный запрос с ошибкой → иначе отбросить и залогировать.
        │
        ├─► D. Нормализация единиц (код по профилю), duplicate_of для повторов, raw_* сохраняются как есть.
        ├─► E. Предметные проверки → issues.csv (правило, связанные записи, страница, цитата).
        └─► F. Экспорт 7 CSV ─► check_submission.py ─► отчёт.
```
- Модель возвращает строго JSON по схеме: никаких «row | metric | k» с ручным разбором.
- Выдумывание подавляется на трёх уровнях: промпт «пусто, если нет в тексте» → обязательная дословная цитата → проверка цитаты кодом.
- Кэш, ретраи, логирование токенов и лимит бюджета на прогон (`budget_usd` в config) сохраняются.
- `MockClient` остаётся только для тестов.

### 3.3. Хранение
- **Каноничные данные** — CSV формата сдачи: `out/<область>/<набор>/*.csv` (`dev`, `test`, `uploads`). Их и сдаём.
- **Промежуточное** — `cache/<область>/<набор>/<pid>/…` (страницы, ответы модели, верификация) — для перезапуска и разбора.
- **Для интерфейса** — DuckDB в памяти, загружается из CSV при старте и после каждой обработки. Отдельная БД-сервер не нужна.
- Загруженные через сайт PDF — `uploads/`, результаты добавляются в набор `uploads` нужной области.

### 3.4. Оценка качества (до прогона test)
`pipeline.score` переписывается на сравнение с эталоном dev **по каждой таблице**:
- результаты — совпадение (статья, метрика, вариант, k, нормализованное значение) + точность связей и источника (страница, цитата);
- сущности (конфигурации / приборы / слои / …) — совпадение по ключевым полям, полнота заполнения полей;
- publications — in_scope, title, year, DOI, authors.
Отчёт `reports/score_<область>_<дата>.md`. Без замера на dev полный прогон test не запускаем.

Сопоставление записей с эталоном (п. 3.5.5): RAG — по (статья, страница, нормализованное значение) + близость названия
метрики (регистр, пробелы, синонимы EM / Exact Match); Solar — по (статья, `metric_name` из закрытого списка,
нормализованное значение, агрегация). Значения с графиков считаются отдельной строкой отчёта.

### 3.5. Нормализация, метрики и проверки

Правила выведены из трёх источников: условия (стр. 5–6, 9–10), README шаблонов и **фактическая разметка эталонов dev**
(как организаторы применяют правила на деле). Скрипты организаторов проверяют только часть правил, остальное — наша ответственность.

#### 3.5.1. Что показали эталоны

| | RAG (37 616 результатов) | Solar (659 результатов) |
|---|---|---|
| Значения **с графиков** | **82 %** (30 818). Из них 28 531 — одна статья D014; без неё — 25 % (2 287 из 8 967) | 20 % (130) |
| Значения с `~` / `≈` в raw_value | 81 % — оцифровка кривых | 1 % |
| Названия метрик | **479 разных**, как в статье (Answer F1, Knowledge precision, NDCG@5, EM…) — закрытого словаря нет | 17: 11 из закрытого списка + доп. (Voc_deficit, Vmpp, Jmpp, AVT, CRI, LUE) |
| Единицы | 78 разных: fraction 78 %, % 13 %, ms, tokens, percentage_points, relative_percent, score… | %, V, mA/cm2, Ohm*cm2 |
| raw_unit | пусто в 95 % — единица не напечатана рядом с числом | заполнен почти всегда |
| Пересчёт raw → normalized | почти всегда **×1** (шкала источника сохраняется); s→ms ×1000; изредка fraction→% ×100 | mV→V ×0.001; fraction→% ×100 (FF, HI) |
| metric_direction | заполнено в 92 % (higher/lower_is_better) | поля нет |

| Замечания (issues) | 134, почти все **уникальные содержательные** (проценты vs п.п., расхождение текста и таблицы, конфликт числа выборки) | 53: contradiction 8, jv_consistency 7, missing_conditions 6, ambiguity 5, derived_values 4… |
| Не нормализуются | — | светимость (`W/m2` остаётся), время отжига (`10 min`), температура (`RT`, `35 ± 5 °C`), `time_unit` (day остаётся) |

#### 3.5.2. Что сейчас не так в коде проекта
1. **Единица почти всегда пустая**: `metric_unit = "%"` только если знак % напечатан у числа, иначе пусто. В эталоне единица заполнена в 99,9 % строк.
2. **`metric_direction` всегда пусто** (в эталоне — 92 %).
3. **Пересчёта единиц нет вообще**: mV не переводится в V, доля FF — в %, секунды — в ms.
4. **Проверка `metric_scale` даёт шум**: при пустой единице число > 1 объявляется «долей вне [0, 1]». Отсюда 1 568 замечаний на dev. Условия прямо запрещают судить о шкале, если она неизвестна.
5. **Проверка `normalization`** помечает любой законный пересчёт (mV→V) как ошибку.
6. **Значения с графиков полностью пропускаются**, а это 82 % эталона RAG и 20 % Solar. Потолок полноты без них: ~18 % по RAG (с D014) / ~75 % (без D014) и ~80 % по Solar.
7. Физических проверок области 1 нет совсем.

#### 3.5.3. Правила нормализации — RAG
- **Шкала источника сохраняется.** Доли и проценты не пересчитываются по одному названию метрики; `metric_unit` при этом **всегда заполняется**: `%` — если проценты указаны (знак, заголовок столбца, подпись оси), `fraction` — если значения даны долями, иначе — единица из статьи (`ms`, `tokens`, `score`…). Пустая единица — только если её действительно нельзя установить.
- Разности процентных метрик — `percentage_points`, относительные улучшения — `relative_percent`; не путать (типичное замечание эталона).
- Время → `ms` (s ×1000, min ×60 000) — при известной исходной единице, исходная пара в `raw_value` / `raw_unit`. Задержка и токены оформляются **результатами метрик**, а не полями `experiments.latency_ms` / `tokens_per_query` (в эталоне эти поля пусты в 142 из 142).
- `raw_value` — как напечатано, со знаками `~ ≈ < ±` и диапазонами; `raw_unit` — только если единица напечатана рядом.
- `metric_value = normalized_value`, `metric_unit = normalized_unit` — иначе **ошибка** скрипта организаторов.
- `metric_name` — как в статье; `metric_variant` — определение (token-level F1, macro, judge-based); `metric_k` — из `@k` в названии (иначе предупреждение скрипта); `top_k` конфигурации ≠ `metric_k`.
- `metric_direction` — по справочнику семейств метрик (accuracy, F1, EM, recall, NDCG, BLEU/ROUGE → higher; latency, error, hallucination, leakage, perplexity → lower) с уточнением моделью по тексту; неизвестно → пусто.
- `aggregation` — свободный текст, только если в статье прямо сказано (mean over queries, macro-average…).

#### 3.5.4. Правила нормализации — Solar
| Показатель | Целевая единица | Пересчёт |
|---|---|---|
| PCE, FF, HI, retained_PCE, stabilized_PCE | `%` | fraction ×100 |
| Voc, Vmpp, Voc_deficit | `V` | mV ×0.001 |
| Jsc, Jsc_EQE, Jmpp | `mA/cm2` | A/m² ×0.1; A/cm² ×1000; µA/cm² ×0.001 |
| Rs, Rsh | `Ohm*cm2` | kΩ·cm² ×1000; MΩ·cm² ×10⁶ |
| T80 | `h` | day ×24; min ÷60 |
| Ширина запрещённой зоны | `eV` | значение в нм в eV **не пересчитываем** — исходное в note |
| Толщина слоя | `nm` | µm ×1000; Å ×0.1 |
| Площадь | `cm2` | mm² ×0.01 |

- Остальное хранится как в статье: светимость и её единица, время и температура отжига, температура измерения, `time_point` / `time_unit`.
- `aggregation` — только `champion` / `mean` / `median`, **пусто**, если в статье не сказано (так в 52 % эталона).
- `metric_name` — 11 значений закрытого списка; дополнительные показатели допустимы, но в оценке не учитываются.
- Словари таблиц (`material_class`, `architecture`, `layer_function`, `scan_direction`…) — значение строго из списка, нестандартная формулировка → ближайшее значение или пусто + исходный текст в `note` (скрипт организаторов даёт **ошибку** на значение вне словаря).
- Прямой и обратный ход развёртки — разные измерения; champion и mean — разные строки результатов.

#### 3.5.5. Проверки → issues.csv
Замечание всегда содержит правило, `record_ids`, описание с числами с обеих сторон, страницу и цитату. Исходная запись не меняется.

**Общие (обе области, код):**
- `contradiction` — одно значение одного объекта в разных местах статьи (текст / таблица / аннотация) различается; повторы с одинаковым значением связываются через `duplicate_of`, с разным — замечание, дублями не объявляются;
- `unit_inconsistency` — единица противоречит значению (FF «0.71 %» при доле 0.71);
- `metric_scale` — **только при известной шкале**: доля вне [0, 1], процент вне [0, 100] для ограниченных метрик (accuracy, precision, recall, F1, EM, Hit, MRR, NDCG).

**RAG (код + модель):**
- `metric_k` — `@k` в названии не совпадает с `metric_k`;
- `percentage_vs_percentage_point` — разность процентов подписана как %;
- `protocol_mismatch` / `comparability` — baseline сравнивается с другим набором, вариантом метрики или протоколом;
- конфликты параметров конфигурации между разделами (модель, top_k, размер выборки) — выявляются моделью на шаге A, подтверждаются цитатами.

**Solar (код, по стр. 6 условий):**
| Правило | Условие |
|---|---|
| `jv_consistency` | \|Voc·Jsc·FF / Pin − PCE\| / PCE > 3 %, Pin = 100 мВт/см² при AM1.5G; один прибор, одно измерение, одна агрегация |
| `voc_limit` | Voc ≥ Eg/q (Eg из материала прибора) |
| `range` | Jsc, FF, PCE вне физических пределов (пороги — см. вопрос в п. 9) |
| `eqe_consistency` | \|Jsc_EQE − Jsc\| / Jsc > 5 % |
| `champion_vs_mean` | среднее по партии больше лучшего прибора той же партии |
| `hysteresis_index` | HI не согласуется с PCE прямого и обратного хода |
| `comparability` | условия не AM1.5G 100 мВт/см² — результат не сопоставим со стандартными |

**Сопоставление** (экран «Сравнение» и правило `comparability`): RAG — одинаковые задача, набор, определение метрики (+k), протокол;
Solar — класс материала, тип прибора, AM1.5G 100 мВт/см², сопоставимая площадь, агрегация, направление развёртки;
сертифицированные значения и стабильность — отдельными группами.

#### 3.5.6. Значения с графиков
По умолчанию: значения **с подписью на графике** (числа на столбцах, в легенде, аннотации) извлекаются vision-моделью со страницы-картинки,
`source_figure` + пометка в `note`; **кривые без подписей не оцифровываются**. Строки `present_not_extractable` массово не создаются —
только когда статья прямо называет значение, а прочитать его нельзя (например, отсылка к supplementary): так в эталонах — 8 строк
в RAG и 6 в Solar; README RAG прямо запрещает подменять этим статусом непроделанную разметку. Это осознанная потеря полноты (п. 3.5.2, пункт 6), её размер покажет замер на dev; решение можно пересмотреть после замера.

## 4. Интерфейс

Сохраняем текущий дизайн и экраны, добавляем:

1. **Переключатель области** (Солнечные элементы / RAG) и **набора** (dev / test / загруженные) в шапке. Колонки таблиц, фильтры и карточки строятся по профилю области, а не зашиты в код.
2. **Карточка записи** — значение (raw → нормализованное), связанные сущности (конфигурация + набор + задача + эксперимент или прибор + слои + материал + условия), замечания, повторы.
3. **Просмотр источника с подсветкой (восстанавливаем фичу).** PDF рендерится через pdf.js на нужной странице, `source_fragment` находится в текстовом слое и **подсвечивается жёлтым** (как прежний `<mark>`), с прокруткой к нему. Для сканов — подсветка по координатам OCR, если их нет — рамка страницы и цитата рядом. Для `source_figure` — страница целиком и пометка «значение с рисунка».
4. **Замечания** — фильтр по правилу и статье, переход к связанным записям и к источнику с подсветкой.
5. **Сравнение** — выбор метрики → таблица и диаграмма сопоставимых результатов, сгруппированных по правилам сопоставления области (RAG: задача + набор + вариант метрики + протокол; Solar: класс материала + тип прибора + AM1.5G + агрегация + развёртка).
6. **Загрузка** — область определяется автоматически (с подтверждением пользователя), лог шагов, стоимость обработки.
7. **Экспорт** — ZIP с 7 CSV набора, готовый к сдаче.
8. **Настройки** — модель, статус ключа (сам ключ не показывается), бюджет.

### 4.1. Все таблицы: навигация и поиск

Решение заказчика: в интерфейсе доступны **все 7 таблиц** каждой области. Условия (стр. 11) требуют от интерфейса поиск,
фильтры, источник и проверки; ниже — как это устроено для всех таблиц сразу. Интерфейс может меняться по ходу работ.

**Контекст в шапке (действует на все экраны):** Область (Солнечные / RAG) → Набор (dev / test / загруженные) → Статья (все или одна).
Выбор статьи сужает все таблицы до неё — так удобно разбирать одну публикацию целиком.

**Переключатель таблиц** на вкладке «Данные» — полоса вкладок с числом строк (с учётом текущих фильтров),
в порядке от статьи к результату (числа условные, для примера):

```
RAG:    Публикации 90 │ Конфигурации 1 240 │ Наборы 68 │ Задачи 31 │ Эксперименты 52 │ ▶ Результаты 9 870 │ Замечания 412
Solar:  Публикации 90 │ Материалы 210 │ Приборы 330 │ Слои 1 900 │ Измерения 160 │ ▶ Результаты 2 400 │ Замечания 180
```
Открывается по умолчанию на «Результатах» — это главная таблица.

**Таблица (любая из 7)** — одинаковое поведение, строится по профилю области:
- поиск по текстовым полям таблицы (с подсветкой найденного в ячейках);
- фильтры по типу поля: словарь → выпадающий список (`material_class`, `result_origin`, `extraction_status`…),
  число → диапазон «от–до» (`metric_value`, `layer_thickness`, `top_k`…), текст → «содержит»;
- активные фильтры показываются плашками над таблицей, каждая снимается крестиком, есть «Сбросить всё»;
- сортировка по любой колонке, серверная пагинация (в RAG десятки тысяч строк);
- выбор колонок: по умолчанию 6–8 ключевых (задаются в профиле), остальные включаются в меню «Колонки» —
  в `results` 27–30 полей, все сразу не помещаются;
- экспорт текущей выборки в CSV.

**Переходы по связям:**
- идентификаторы-ссылки в ячейках (`config_id`, `dataset_id`, `device_id`, `material_id`, `measurement_id`, `record_ids`…)
  — кликабельные плашки: открывают карточку связанной записи;
- **карточка любой записи** (выезжающая панель справа): все поля записи (пустые скрыты под «показать пустые»),
  блок «Связано» — родители и дочерние записи с количеством, например у конфигурации: «Результаты: 342 → показать в таблице»,
  у прибора: «Слои: 6 · Измерения: 2 · Результаты: 18», у результата — прибор + материал + измерение или конфигурация + набор + задача + эксперимент;
- «показать в таблице» переключает таблицу и ставит фильтр-плашку вида `config_id = C3 (D007)`;
- внутри панели — история переходов с кнопкой «Назад», чтобы пройти цепочку результат → конфигурация → её результаты и вернуться;
- у записей с источником (`results`, `issues`) — кнопка «Открыть источник»: PDF на странице с подсвеченной цитатой;
- у слоёв прибора — схема стека слоёв (полосы по `layer_order` с функцией и толщиной) в карточке прибора.

**Общий поиск** (поле в шапке, горячая клавиша `Ctrl+K`): ищет сразу по всем 7 таблицам текущей области и набора,
показывает результаты, сгруппированные по таблицам: «Результаты 120 · Конфигурации 5 · Наборы 2 …» с первыми совпадениями
в каждой группе. Клик по записи открывает её карточку, клик по группе — таблицу с этим запросом. Поиск понимает
идентификаторы (`D007`, `D007/R015`, `C3`) и открывает запись напрямую.

**Состояние в адресе страницы:** область, набор, таблица, фильтры и открытая запись хранятся в URL, поэтому работает кнопка
«Назад» браузера, а ссылку на конкретную выборку или запись можно отправить (удобно на защите).

**Бэкенд** (одинаковый для областей, связи берутся из профиля):
- `GET /api/{area}/{set}/tables` — список таблиц, число строк, метаданные колонок (тип, словарь, колонки по умолчанию);
- `GET /api/{area}/{set}/tables/{table}?q=&f.<поле>=&min.<поле>=&max.<поле>=&sort=&page=` — строки таблицы;
- `GET /api/{area}/{set}/record/{table}/{pid}/{id}` — запись + связанные записи по всем направлениям;
- `GET /api/{area}/{set}/search?q=` — общий поиск, счётчики по таблицам и первые совпадения.

## 7. Бюджет и риски

- **Стоимость.** Точную цифру дам после этапа 2 (замер на 3 статьях dev с подсчётом токенов). Порядок: десятки–сотни тысяч входных токенов на статью; эталон RAG очень плотный (в среднем ~1 800 результатов на статью), поэтому основная статья расхода — выходные токены. Лимит бюджета на прогон задаётся в config и прерывает прогон.
- **Плотные таблицы RAG** (сотни чисел на страницу) → вызов на таблицу, а не на страницу; при обрыве ответа — дробление.
- **Сканы** (≈15 % RAG) → vision-OCR моделью, уже реализован; качество проверяем на D002/D013/D021.
- **Значения с графиков** — 82 % эталона RAG (в основном одна статья D014) и 20 % Solar. Подписанные значения читаем vision-моделью, кривые без подписей не оцифровываем (п. 3.5.6). Главный риск для полноты.
- **Нет точных порогов физических проверок** Solar: слайд ссылается на «описание кейса», которого нет в материалах. Без него — разумные пороги с пометкой в паспорте.
- **Лимиты API** → параллелизм и backoff уже есть.
