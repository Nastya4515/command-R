## 2. Исходное состояние (проверено)

- Конвейер `pipeline/`: read_pdf → fragments → model → assemble → export → check. На dev с MockClient: точность 81.1 %, полнота 81.9 %, check_submission — 0 ошибок.
- Бэкенд FastAPI + DuckDB: 8 эндпоинтов + загрузка PDF с фоновой обработкой и опросом статуса (`/api/jobs/{id}`).
- Фронтенд React: Обзор / Данные / Замечания / Публикации / Загрузка (drag-and-drop работает).
- Клиенты модели: `mock`, `file`, `local` (LoRA), `api` (OpenAI-совместимый; backoff, кэш ответов, подсчёт токенов).
- Ключи: `OPENAI_API_KEY` — проверен, работает. Gemini — геоблок. OpenRouter — 50 зап/день.
- Сканы D002/D013/D021 (и сканы в test) не читаются — нет OCR (Tesseract не установлен).

## 3. Задачи доработки

### P0 — блокирует сдачу

**P0-1. Перевести конвейер на OpenAI.**
`config.yaml`: `model.client: api`, `base_url: https://api.openai.com/v1`,
модель `gpt-4o-mini` (дешёвая, с форматом справляется; для спорных случаев — `gpt-4.1`).
Ключ читается из `.env` (уже реализовано в ApiClient; добавить fallback на `OPENAI_API_KEY` из env).
Критерий готовности: дымовой тест на 3 статьях test — ответы парсятся, доля «нет» разумная, нет выдуманных значений (контроль assemble).

**P0-2. Пакетирование запросов (батчинг фрагментов).**
До 8 текстовых фрагментов одной статьи в один запрос (нумерованный ответ по каждому).
Цель: ~25 тыс. фрагментов test → ~4–5 тыс. запросов; ускорение прогона в 5–8 раз, экономия ~40 %.
Критерий: на dev-выборке (3 статьи) score с батчингом не хуже, чем без, минус ≤ 2 п.п.

**P0-3. Полный прогон test-набора (90 PDF).**
Команда: `python -m pipeline.run --set test`. Кэш ответов делает перезапуск бесплатным.
Бюджет: ~10–12 М токенов входа + ~2 М выхода ≈ 3–5 $ на gpt-4o-mini.
Критерий приёмки (dev-ТЗ): `publications.csv` — 90 строк; `check_submission out/test test` — код 0 или 2, все предупреждения разобраны; в CSV нет NaN/None/null.

**P0-4. Разбор issues и предупреждений чекера на test.**
Механические замечания (metric_scale, contradiction, metric_k) просмотреть выборочно (≥ 50 шт.), классифицировать «истинное/ложное», ложные — фильтром в checks.py. Итог — абзац в паспорте: сколько замечаний, каких, что означают.

**P0-5. Паспорт датасета (`docs/DATASET_PASSPORT.md`).**
Таблицы и ключи; каждое поле: тип, единицы/шкала, обязательность, откуда берётся; правила нормализации (доли↔%, ↓/↑, склейка чисел); правила замечаний; известные ограничения (сканы без OCR, графики без оцифровки, mock-поля конфигураций).

### P1 — сильно влияет на оценку/защиту

**P1-1. Сайт на боевых данных.** После P0-3: `POST /api/reload` на `out/test`; стартовый экран пустой (данные = загруженное + test по переключателю в README). Проверить сценарий судьи: загрузить любую test-статью через сайт → лог → результат с цитатой и PDF.

**P1-2. Экран «Сравнение» (Should по dev-ТЗ).** Выбор метрики (+k) → таблица и диаграмма сопоставимых результатов по конфигурациям. Простой вариант: фильтр по metric_name/metric_k + bar chart.

**P1-3. Подсветка цитаты в PDF-просмотрщике (Should).** Сейчас открывается страница; добавить выделение source_fragment через pdf.js text layer.

### P2 — если останется время

**P2-1. OCR сканов.** Установить Tesseract, `ocr_enabled: true`, прогнать сканы dev/test. Закрывает ~15 % полноты на сканах.
**P2-2. Дедупликация текст-текст.** Связывать идентичные текстовые повторы через `duplicate_of` (сейчас только текст→таблица).
**P2-3. Аудит metric_scale (1568 замечаний на dev).** Ужать правило после выборочной проверки.
**P2-4. OllamaClient (Could).** Локальный fallback без внешних API (кандидат для рассказа на защите про автономность).

## 4. Нефункциональные требования

- Воспроизводимость: прогон из README одной командой; кэш шагов — повторный запуск продолжает с места сбоя.
- Деньги: прогон test ≤ 5 $; каждый запрос к API логируется с токенами (уже есть).
- Тесты: 16 pytest + ruff зелёные после каждого изменения; smoke-тест ApiClient на 3 статьях перед полным прогоном.
- Безопасность: ключи только в `.env` (в .gitignore); в коде, логах и CSV ключей нет.
